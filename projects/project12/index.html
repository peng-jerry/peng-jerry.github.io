Noteable

15-113

Project 2

Skills: React, Vite, Python, Flask, SQLAlchemy, PostgreSQL (incl. full-text search), JWT authentication, REST API design, drag & drop, HTML canvas, camera (getUserMedia), testing, Render, Neon & GitHub Pages deployment

A full-stack note-taking app: sign up, write notes in Markdown with a live preview, and organise them with nested folders and coloured tags. Notes can link to each other with [[wiki links]], hold doodles, photos and tables, start from templates, keep a version history, and go to a trash you can restore from. Everything saves automatically as you type (even through a dropped connection), the panes can be resized or collapsed, and the layout adapts from a three-pane desktop view down to a phone.

Three Deployed Pieces

The frontend is a React single-page app built with Vite, and the built copy is served straight from this site at /projects/noteable/. It talks to a Flask REST API hosted on Render, which stores everything in a PostgreSQL database on Neon. Database migrations (Alembic) run automatically on every deploy. The app uses hash URLs (/projects/noteable/#/notes/…) on purpose: GitHub Pages only knows this site’s own 404 page, so ordinary deep links would break as soon as someone refreshed.

Accounts and Private Routes

Logging in returns a short-lived access token and a longer-lived refresh token. When an access token expires, the frontend quietly swaps the refresh token for a new one and retries the request; if several requests expire at once, they share a single refresh. Logging out revokes both tokens on the server, and changing your password invalidates every older session. On the frontend, routes are split into public (the landing page), public-only (login and register) and private (your notes and settings). Visiting a private page while logged out sends you to the login page, then back to where you were going. On the backend, every query is scoped to the signed-in user, and someone else’s note returns the same 404 as a note that doesn’t exist, so IDs can’t be probed.

Folders Inside Folders

Folders form a tree through a single parent_id column. The API rejects moves that would put a folder inside itself or one of its own subfolders, caps nesting at ten levels, and keeps sibling names unique. Folders can be starred to pin them to the top of the sidebar, and notes and folders can be dragged onto other folders (with a long-press on touch screens). Deleting a note or folder moves it to a trash for 30 days rather than destroying it: everything trashed together is tagged with the folder it went with, so restoring the folder brings back exactly that set, back to where it was if possible, or to the top level (renamed if the old name has since been taken) if not.

Tags, Search and Sorting

Tags are created on the fly as you type them into a note, with autocomplete, and get a colour that works in both light and dark themes; the sidebar lists them with counts, and selecting several shows only notes that have all of them. Search matches partial words in titles and content, ranks results with PostgreSQL’s full-text search (title matches count for more), highlights the matched words in the results, and understands tag:exam filters and "quoted phrases". There are eight sort orders, the choice is remembered separately for each folder or view, and inside a folder you can switch to a manual order and drag notes into place.

Linked Notes and Version History

Typing [[ in the editor suggests note titles; the preview turns links into working links, and a link to a note that doesn’t exist yet creates it when clicked. The server records each link’s target, so renaming a note rewrites the [[link text]] in every note that points to it, and a details panel shows which notes link to the current one, alongside a clickable outline of its headings and word count and reading time. Autosave also keeps a snapshot of a note at most every ten minutes while you edit (plus named snapshots on request, up to 50 per note). The history view shows a line-by-line diff against the current text, and restoring a version saves the current text as a version first, so nothing is ever lost by restoring.

Templates, Import and Export

New notes can start from five built-in templates or your own — any note can be saved as one — with placeholders like {{date}}, {{weekday}} and {{folder}} filled in from your own clock and locale. Import takes Markdown or text files, or a .zip that’s unpacked in the browser and recreated as folders; files are sent in batches so a large archive never exceeds the API’s request limit. Notes export as .md, .txt or a print-ready PDF, and a folder (or everything) exports as a .zip whose files carry a small header with their title and tags — so an export imports back in with its structure and tags intact, doubling as a backup.

Doodles, Photos and Tables

The editor’s toolbar can insert a doodle, a picture or a table. The doodle pad draws on an HTML canvas with a pen (whose line thickens with stylus pressure), a highlighter and an eraser, and it saves both a PNG and the strokes themselves — so a doodle can be reopened later and drawn on some more, updating in place in every note that shows it. “Take a picture” opens a live camera preview right in the page (on a laptop webcam or a phone’s front or back camera), with a fallback to choosing an existing image; large photos are shrunk in the browser before they’re uploaded. Pictures are stored in the database and are private to their owner, so the page fetches them with the login token rather than linking to them, and the server checks each file’s actual bytes rather than trusting its name (SVG, which can carry scripts, isn’t accepted). Exports include the pictures in an images folder and imports put them back, with doodles still editable. The table button opens a size picker, and inside a table Tab and Shift+Tab move between cells, add a row at the end and keep the columns lined up. List buttons work on an empty line, Tab nests list items with outline numbering (1. → a. → i., • → ◦ → ▪) that renumbers itself, and checklist items can be ticked straight from the preview.

Autosave Without Lost Edits

There’s no save button. Edits are sent about a second after you stop typing, and only the fields that changed are sent. Saves never overlap: anything typed while one is in flight is merged and sent next, so they can’t arrive out of order and overwrite newer text with older text. Until the server confirms a save, the unsent changes are also kept in the browser: if the connection drops, the editor says so, retries with back-off and sends them the moment it’s back online; if the tab is closed first, reopening the note offers to restore them. Switching notes saves whatever is pending, and the browser warns you before closing a tab with unsaved work.

Built to Grow

Noteable is meant to be the first piece of a larger site, so the backend isn’t notes-specific at its core. Every feature is its own Flask blueprint under a versioned /api/v1 prefix, user accounts are shared rather than tied to notes, and every error — validation, authentication, database outages — comes back in the same JSON shape with a stable error code. Adding a new section later means adding a package, not rewriting this one.

Testing, and the Bugs It Caught

The backend has 75 pytest tests, run against both SQLite and a real PostgreSQL server, and the frontend has 73 Vitest tests. On top of that, scripted headless-browser runs click through every feature against the real API at desktop, tablet and phone sizes — dragging notes and folders, importing a zip, going offline mid-edit, closing the tab and recovering the draft, drawing doodles, and taking pictures with Chromium’s simulated camera. Those runs caught bugs the unit tests couldn’t: deleting the folder you were viewing left the app stuck on a folder that no longer existed, a dialog could wipe text typed the instant it opened, drag-and-drop announced internal IDs to screen readers instead of note names, and a picture inserted right after a table quietly became part of it. Testing the database migration against a Postgres copy with existing rows caught one that would have broken the live deploy outright: a new column’s default value was written in a form SQLite accepts but PostgreSQL rejects. The first deployment caught two more. Render had been running its default start command instead of the project’s, and the service URL turned out not to be the one the frontend expected — the default name was already taken by someone else’s service. Checking that the health endpoint reported this API (and a working database) before building is what caught it.
