PDF Combiner

15-113

HW 4

Skills: Python, Flask, REST APIs, CORS, JavaScript, Render & GitHub Pages deployment

A two-part “backend + frontend” assignment: upload several PDFs, drag them into the order you want, and get back one merged file. The frontend here only handles the UI — every byte of PDF processing happens on a separate Flask API hosted on Render.

Open the PDF Combiner

Select 2+ PDFs, reorder them, and download the combined result — nothing is stored server-side

Two Separately Deployed Halves

The frontend is a dependency-free HTML/CSS/JavaScript page (the copy embedded above lives right in this site’s repo). The backend is a Flask API, merging PDFs with the pypdf library and served in production by Gunicorn, deployed separately on Render. They only ever talk to each other over the network — the frontend never imports or calls the backend’s code directly, which is the actual point of the assignment: practicing a real client/server split instead of one monolithic app.

How a Combine Request Works

Selected files are collected into a JavaScript array in the order the user arranges them, packed into a FormData object (each file appended under the same field name, files), and sent with fetch() as a multipart/form-data POST to /api/combine. On the backend, Flask reads that file list in the same order, validates every file (extension, magic bytes, that pypdf can actually parse it, size limits) before merging any of them, then walks through each validated PDF in order appending its pages to a single output with pypdf.PdfWriter. The response’s body is the merged PDF itself, not JSON, so the frontend reads it as a Blob and turns that into a download link with URL.createObjectURL().

CORS, and a Bug It Actually Caught

Since this frontend and the Render backend live on different origins, the backend has to explicitly allow this site’s origin via CORS — restricted to a specific origin list rather than a wildcard, so the API can’t be silently called from just anywhere. Setting that up caught a real, easy-to-miss bug: the allowed-origin environment variable on Render was originally entered with a trailing slash (https://peng-jerry.github.io/), which never matches the Origin header a browser actually sends (no trailing slash) — every request would have failed CORS silently, looking exactly like the backend was down. Fixed by removing the slash and re-verifying with a real cross-origin request before calling it done.

Validation, Twice

The frontend does a quick sanity check (file extension) purely for immediate feedback — so a user isn’t left guessing why a request failed 10 seconds later. The backend never trusts that check: it independently verifies every file’s magic bytes and actually parses it with pypdf, rejects anything corrupted, password-protected, or oversized, and only merges if every single file passes. Client-side validation is a UX nicety here, not a security boundary.
